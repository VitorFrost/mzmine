# MZmine v4.0.8 governed mzML import and centroid parity

## Purpose

This record documents the first direct behavioral comparison between the frozen public MZmine
v4.0.8 scientific source slice and the independent open-offline fork.

The governed scope is deliberately narrow:

- import the same non-IMS LC-MS mzML bytes;
- preserve scan order and scan identity;
- normalize scan, spectral, and precursor metadata;
- apply the public centroid mass detector at an explicit noise level of `0.0`;
- allow the source-data stream to be selected explicitly as MS1 or MS2;
- compare every normalized import and mass-detection record.

The comparison does not infer the instrument manufacturer, acquisition mode, or source MS level.
Manual workflow dispatch executes only the selected level. Push and pull-request CI use two explicit
matrix jobs, one for MS1 and one for MS2, so both user-selectable paths remain validated.

## Independent producers

The v4.0.8 report is generated by the compiled public parser/centroid source slice. The candidate
report is generated independently by:

`src/test/java/io/github/mzmine/parity/OpenOfflineDifferentialReportMain.java`

The candidate producer calls the fork's own:

- `MzMLFileImportMethod`;
- MSDK `MsScan` records;
- `CentroidMassDetector.getMassValues(double[], double[], double)`.

It does not construct a project, create feature lists, start the GUI, call account/cloud services, or
reuse oracle output. The producer is contained in the validation test source set and does not become
part of the distributed application.

## Normalized comparison contract

Every imported scan is keyed by its zero-based ordinal position in the original mzML stream. The
import stage records all scans. The mass-detection stage records only the explicitly selected source
MS level.

Compared fields include:

- scan key and scan number;
- MS level;
- polarity;
- spectrum type;
- point count;
- retention time in minutes;
- minimum and maximum m/z;
- summed intensity;
- first, middle, and last spectral points;
- precursor MS level;
- activation method and energy;
- isolation-window bounds and isolation m/z;
- precursor charge and parent scan number.

Counts, membership, exact fields, provenance, and numerical fields are all compared. Missing and
extra records are retained as differences rather than reduced to a pass/fail count.

## Failures discovered before parity assessment

### F-015 — Gradle working-directory path resolution

The first Java execution resolved the relative mzML path below the standalone Gradle project. The
parser never opened the file. The correction supplies physical paths derived from
`GITHUB_WORKSPACE`, while the canonical report retains only the portable dataset identity.

### F-016 — legacy cached MSDK destination-array behavior

The initial candidate report read each spectrum twice. The legacy MSDK implementation decoded into
caller-supplied arrays on the first call, but when internal arrays were cached, a second call with a
new sufficiently sized destination returned that unpopulated destination. This produced zero arrays
only in the validation producer.

The correction is limited to the producer: it requests parser-owned arrays with
`getMzValues(null)` and `getIntensityValues(null)`, then copies exactly the declared point count. A
regression test locks this behavior. No production parser or centroid algorithm was changed.

### F-017 — deterministic binary32 retention-time representation

After F-016, all remaining strict differences were retention times. For all 5,221 scans, the fork
value is reproduced exactly by:

```text
candidate_minutes = float32(float32(reference_minutes) * 60) / 60
```

The legacy parser stores seconds as binary32; the v4.0.8 parser retains minutes as binary32. The
maximum observed displacement was:

- `1.017252603929819e-6 min`;
- `6.1035156235789145e-5 s`;
- approximately 61 microseconds;
- maximum relative error `5.9528752522436796e-8`.

This is bounded by half the IEEE-754 binary32 relative spacing and is not a chromatographic shift.
The strict evidence remains preserved. A separate versioned tolerance contract is used only for the
governed equivalence decision.

### F-018 — transient Windows dependency HTTP 403

One Windows job received HTTP 403 responses from Maven Central while resolving established Gradle
plugin dependencies, before compilation. No dependency or repository configuration was changed.
The same commit subsequently passed Windows dependency resolution, compilation, tests, startup,
batch execution, and comparison with the untouched 3.9 baseline, confirming the transient diagnosis.

- applies only to retention time;

## Cross-platform regression gates

The final MS1/MS2 matrix head passed:

- independence and public-data policy;
- Linux compilation and tests;
- Windows compilation and tests;
- no-login headless startup;
- deterministic batch execution;
- equality with the untouched MZmine 3.9.0 baseline;
- public v4.0.8 source closure and adapter lock;
- exact dataset-byte verification;
- explicit MS1 and MS2 oracle/candidate execution;
- strict difference retention;
- governed zero-difference requirements.

## What this proves

For the frozen public mzML file, explicit settings, and declared comparison contract, the
open-offline fork is behaviorally equivalent to the public MZmine v4.0.8 source slice for:

- mzML scan import;
- scan ordering and membership;
- MS-level, polarity, and spectrum metadata;
- spectral m/z and intensity values;
- precursor/isolation/charge metadata exercised by the file;
- centroid mass detection at noise `0.0`;
- both explicitly selectable MS1 and MS2 source-data paths.

## What this does not prove

This result does not establish parity for:

- profile-mode peak picking or other mass detectors;
- scan filters or advanced import processors;
- chromatogram construction;
- feature resolution/deconvolution;
- isotope grouping;
- alignment, blank filtering, gap filling, or duplicate removal;
- spectral-library matching or candidate ranking;
- ion mobility;
- other mzML encodings, compression modes, malformed files, or manufacturers;
- memory, cancellation, performance, packaging, or release behavior.

## Next scientific gate

The next direct differential stage is chromatogram construction and feature detection. It must:

1. start from the now-validated import and centroid records;
2. freeze semantically equivalent parameters for v4.0.8 and open-offline;
3. emit chromatogram membership, scan range, m/z, RT, intensity, point count, and status records;
4. preserve every strict difference before repair;
5. separate representation differences from algorithmic differences;
6. validate MS1 first, while retaining the explicit MS2 source-data path for later association work;
7. avoid project, GUI, account, cloud, or manufacturer-inference dependencies unless scientifically required and explicitly reviewed.
